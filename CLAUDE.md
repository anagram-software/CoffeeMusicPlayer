# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Coffee Music Player: an Android local-music player (package `com.udeshcoffee.android`, published on the Play Store). Single `:app` module, mostly Kotlin with a few legacy Java files. minSdk 26, compileSdk 37.1 (`release(37) { minorApiLevel = 1 }`, required by Compose 1.13), targetSdk 37.

**No backward compatibility.** Everything since "Modernize build system (Phase 0)" is a new version with breaking changes: every install is a fresh install, with no upgrade path from the Play Store release. Don't write migrations or compatibility code (database, preferences, saved queue, server data); the Room schema stays at version 1 until this version ships.

A phased modernization (2026) is done: 0 build system, 1 target SDK 37 (scoped storage, permissions), 2 Media3 playback, 3 coroutines/Flow, Coil, Retrofit 3, 4 Compose + Material 3 UI, 5 hardening (R8, baseline profiles, StrictMode, tests, CI). Possible follow-ups: SharedPreferences → DataStore, RemoteViews widgets → Glance.

## Build & test

Gradle 9.9 wrapper, AGP 9.5 (built-in Kotlin, no `kotlin-android` plugin), Kotlin 2.4 (K2), KSP. Kotlin DSL build scripts, versions in `gradle/libs.versions.toml`. Builds on JDK 21 (bytecode target 17). Repositories are `google()` + `mavenCentral()` only.

```
./gradlew assembleDebug
./gradlew installDebug
./gradlew lintDebug                                                   # fails only on issues not in app/lint-baseline.xml
./gradlew test                                                        # JVM unit tests
./gradlew test --tests 'com.udeshcoffee.android.playback.QueueOrderTest'   # single test class
./gradlew :app:connectedDebugAndroidTest                              # instrumented tests (emulator/device; reinstalls the app, wiping its data)
./gradlew assembleRelease                                             # R8-minified, unsigned
./gradlew :app:generateBaselineProfile                                # regenerate the baseline profile (API 33+ emulator/device)
./gradlew :baselineprofile:connectedBenchmarkReleaseAndroidTest       # startup benchmark (physical device; refuses emulators)
```

CI (`.github/workflows/ci.yml`) runs debug + release builds, lint and unit tests, plus the instrumented tests on an API 35 emulator.

`local.properties` is untracked. Besides `sdk.dir` it holds API keys, which become `BuildConfig` fields (missing keys build as empty strings):
```
lastfm.apiKey=...
```

**Tests.** JVM unit tests in `app/src/test` cover pure logic: queue encoding (`QueueStore`), visible-shuffle ordering (`QueueOrder`), album/artist grouping (`Operators`), sorting, repeat modes, Subsonic auth/URLs/mapping (`song(...)` in `TestData.kt` builds test songs; android.jar stubs return defaults). Keep logic testable by pulling it out of Android/Media3 classes, as `QueueOrder` is out of `SessionPlayer`. Instrumented tests in `app/src/androidTest`: Compose component tests.

**Release hardening.** Release builds use R8 with resource shrinking; library rules come from their consumer rules, app rules (jaudiotagger, Jsoup) are in `app/proguard-rules.pro`. Test anything reflective in a release build. The baseline/startup profile in `app/src/release/generated/baselineProfiles/` is generated by the `:baselineprofile` module (journeys in `Journeys.kt`; regenerate after big UI changes) and installed by `profileinstaller`. Debug builds enable StrictMode (log only): keep disk and network work off the main thread, including in composition (use `produceState`/`LaunchedEffect` with `Dispatchers.IO`).

`MainActivity` uses the window theme `Theme.Coffee` (Material3 DayNight NoActionBar; real colours come from the Compose theme). `AppTheme` (`Theme.MaterialComponents.NoActionBar.Bridge`) remains only for the View-based widget configuration activity.

**K2 gotcha:** a lambda whose last expression is a `when`/`if` containing `null` branches can infer a nullable return type; watch for this where a non-null result is required.


**Platform rules (targetSdk 37):**
- Permissions are requested with the Activity Result API. Use `utils/Permissions` (`readAudio` is `READ_MEDIA_AUDIO` on 33+, `READ_EXTERNAL_STORAGE` below), never check `READ_EXTERNAL_STORAGE` directly.
- Modifying or deleting songs goes through `utils/MediaAccess` (`createWriteRequest` / `createDeleteRequest` consent dialogs on API 30+, launched with `StartIntentSenderForResult`). Files are never written by path; the tag editor copies to cache, edits with jaudiotagger, and writes back via `ContentResolver.openOutputStream(uri, "wt")`.
- The library is read from MediaStore only, never by listing the file system (there's no folder browser).
- Activities are drawn edge to edge (`enableEdgeToEdge()`). Compose screens get insets from `Scaffold`/`safeDrawingPadding`; the View-based widget config screen uses `padForSystemBars()` (`extensions/InsetsExtensions.kt`).
- Back handling uses `OnBackPressedCallback` (predictive back is enabled); call `onBackPressedDispatcher.onBackPressed()`, not `onBackPressed()`.
- PendingIntents are `FLAG_IMMUTABLE`.
- Home-screen widget buttons send media key events to Media3's `MediaButtonReceiver` (explicit, immutable PendingIntents with distinct request codes).

## Architecture

**DI (Koin 4).** `App.onCreate` calls `startKoin { androidContext(...); modules(appModule) }`. Composables get ViewModels with `koinViewModel()` (parameterised ones with `koinViewModel(key = ...) { parametersOf(id) }`) and singletons with `koinInject()`. Modules live in `di/`:
- `RepositoryModule`: Room database (single) and DAOs (`DataDao`, `PlaylistDao`), `RemoteDataSource`, `LocalDataSource`, `DataRepository`, `MediaRepository`
- `ComposeModule`: every ViewModel. New ViewModels must be registered here.
- `CommonModule`: the default `SharedPreferences`

**Two music sources, one at a time.** Songs come from the device (MediaStore) or a Subsonic / OpenSubsonic server such as Navidrome (`data/subsonic/`). The user picks one in Settings ("Music source"), stored by `MusicSourceStore` (`data/source/`, default prefs key `music_source`). `SERVER` is the default: new installs start on it but not `isConfigured` (signed out), so the app opens on Settings with an inline sign-in form plus "Use music on this device only", and the music screens show a setup prompt (`SetupNeeded` in `CoffeeApp`). Once set up, Settings shows the source with a confirmed "Change", which signs out and returns to setup (`MusicSourceSwitcher.change`). Everything follows the source: Library (`DeviceLibraryScreen` or `ServerLibraryScreen`), search, favorites (app favorites or server stars), playlists, the add-to-playlist dialog, the restored queue, Android Auto (`LibraryBrowser`) and voice search. It's a rare, one-time choice, not a hot swap: `ui/MusicSourceSwitcher` clears the queue and restarts the activity task (not `recreate()`, which would keep ViewModels), so screens and ViewModels read `MusicSourceStore.current`/`isServer` once at creation. Switching to the device signs out of the server. In server mode the app doesn't ask for the audio files permission. **Offline listening** is part of the server source (not a third source), in `data/download/DownloadRepository`: server songs download as Media3 downloads (`DownloadManager`, run by `playback/DownloadsService`, a `dataSync` foreground `DownloadService` with a progress notification and no scheduler) into a `SimpleCache` in the app's external files dir (`downloads/`, excluded from backup with Media3's `exoplayer_internal.db`). Each download's ID and `customCacheKey` is the song's media ID (`subsonic:<id>`), the same key its `MediaItem` carries, and `playbackMediaSourceFactory` reads through a read-only `CacheDataSource` on that cache, so downloaded songs play from storage (whatever the stream URL, token, format or bit rate) and the rest stream. Downloads store a `ServerSong` snapshot (shared with `QueueStore`) so the "Downloads" smart playlist (`Playlist.DOWNLOADS`, first in the server Playlists tab, also linked from Home when the server is unreachable) works offline. UI: song sheet Download / Stop / Remove download, collection sheets Download / Remove downloads, `DownloadButton` in server album and playlist top bars (download, progress ring to stop, downloaded to remove after `AppDialog.RemoveDownloads`), a badge on downloaded `SongRow`s (`LocalDownloadedIds`), and "Download on Wi-Fi only" (Media3 `Requirements`) in the server settings. Downloads use the streaming quality/format settings; cover art is prefetched into Coil's disk cache. Leaving the server (`MusicSourceSwitcher`) removes all downloads. Media3 reports no progress, so `DownloadRepository` polls `currentDownloads` while any run; `downloadSummary` (unit tested) sums a song set's state. Server items use the same models with `remoteId` (and `coverArt`, `albumRemoteId`, `artistRemoteId`) set; their Long `id` is a stable negative hash of the Subsonic ID (`RemoteIds`), so Long-keyed code (lists, queue, routes, sorting) works for both and MediaStore IDs (positive) never collide. Branch on `song.isRemote` / `remoteId != null` where behaviour differs. Device playlists hold device songs and server playlists server songs; file operations (edit tags, share, delete) are device-only.

**Data layer (`data/`).** Three repositories with separate jobs:
- `MediaRepository` handles the device music library through `MediaStore` (songs, albums, artists, genres, folders) plus user playlists, which live in Room (`playlists` / `playlist_items`, holding MediaStore song IDs; MediaStore playlists are deprecated and not used). `observe…` functions return Flows that re-query when MediaStore changes (a `ContentObserver` `callbackFlow`, combined with Room flows where relevant); `load…`/suspend functions are one-shot. Albums and artists are built from song lists in `data/media/Operators.kt`.
- `DataRepository` handles app-owned data (favorites, play stats, artist bios), combining `LocalDataSource` with `RemoteDataSource`.
- `SubsonicRepository` (Koin single) is the music server: sign-in (`ping`, OpenSubsonic extensions), library (`search3` with an empty query for all songs, paged; `getAlbumList2` paged; `getArtists`, `getGenres`, `getAlbum`, `getArtist`, `getArtistInfo2`, `getSongsByGenre`), playlists (`createPlaylist`/`updatePlaylist`/`deletePlaylist`; reordering replaces the list), stars as favorites (`starredIds` StateFlow, updated optimistically), lyrics (`getLyricsBySongId` with the `songLyrics` extension, else `getLyrics`), `scrobble`, and stream/cover URLs. **Octo-Fiesta** (a proxy that mixes Qobuz/Deezer results into the API; IDs `ext-<provider>-<type>-<id>`, and streaming one makes the server download it) adds provider items to `search3` but also to `getArtist` (albums), `getAlbum` (missing tracks) and `getTopSongs`, found by searching the provider by name. So detail pages show the library first, the provider separately (`data/subsonic/External.kt`: `groupReleases`, `splitAlbumTracks`, cover filtering, unit tested; as in the web player): a server artist page is one `getArtist` plus top songs and similar artists (no `getAlbum` per album on open), and playing an album or artist plays only its library songs (`albumSongs`/`artistSongs`). Tapping a provider song plays just that song. "Add to library" on albums with provider tracks (`addAlbumToLibrary`) stars the provider album, which Octo-Fiesta turns into a download, or else starts and drops each missing song's stream; requests are remembered for the session only (`addedAlbums`), as no progress is reported. Calls are main-safe and throw `SubsonicException` (`isAuthError` for codes 40/41/44); UI code catches it and shows a message or a retry. `SubsonicClient` builds token-auth URLs (`u`, `t = md5(password + salt)`, `s`, `v`, `c`, `f=json`) and unwraps `subsonic-response`; DTOs (`SubsonicDtos.kt`) ignore unknown fields. Only the salt and token are stored, never the password, in the `subsonic` SharedPreferences file, which `backup_rules.xml` / `data_extraction_rules.xml` exclude from backup. Cleartext HTTP is allowed (`network_security_config.xml`) for LAN servers; the UI warns about non-HTTPS servers. Test against `demo.navidrome.org` (user `demo`, password `demo`). The web player in `~/Projects/CoffeeMusicPlayerWeb` uses the same API.
- All HTTP goes through one OkHttp client (`data/remote/Http`).
- `local/LocalDatabase` is Room DB `CoffeePlayer.db` (Room 2.8, KSP), version 1. DAOs are `suspend`/`Flow`; main-thread queries are not allowed. Schemas are exported to `app/schemas/` (commit them). Before release, change the schema in place at version 1 (no migrations; reinstall to test). After this version ships, schema changes need a version bump and a `Migration` in `RepositoryModule`.
- `remote/RemoteDataSource` is a Kotlin `object` (Retrofit 3 + OkHttp 5 + kotlinx.serialization, all `suspend`, returning null/empty on failure). It covers Last.fm (artist info, artist image scraped from the artist page with browser headers and Jsoup, and `track.getInfo`/`track.search` for the tag editor's metadata lookup; Last.fm has no release year). The API key comes from `BuildConfig` and goes in as a query param via an OkHttp interceptor. The service is built lazily on the IO dispatcher (`lastFm()`).
- **Lyrics come only from the music server** (`SubsonicRepository.lyrics`: `getLyricsBySongId` with the `songLyrics` extension, else `getLyrics`), loaded by `LyricsViewModel` and not stored locally. Device songs have no lyrics, so the player hides the lyrics toggle for them.
- Coroutines/Flow throughout (no RxJava). Repository functions are main-safe. ViewModels expose `StateFlow` (repository flows via `stateIn(viewModelScope, ...)`), collected with `collectAsStateWithLifecycle()`; no LiveData. Fire-and-forget writes that must outlive a screen use `utils/ProcessLifecycleScope`.

**Playback (`playback/`, Media3).**
- `PlaybackService` is a `MediaLibraryService` owning an ExoPlayer. Media3 provides the notification, foreground state, media buttons (`androidx.media3.session.MediaButtonReceiver`), audio focus, becoming-noisy and playback resumption (`onPlaybackResumption`). The service adds queue persistence (`QueueStore`), play counts, widget updates, the "on call" setting, voice search, and a browse tree for Android Auto (`LibraryBrowser`).
- The session exposes `SessionPlayer` (a `ForwardingSimpleBasePlayer`), not ExoPlayer directly. It implements fade on play/pause and the app's **visible shuffle**: shuffling reorders the queue itself (current song first) instead of ExoPlayer's hidden shuffle order, so queue indices in the UI are always play order. ExoPlayer's own `shuffleModeEnabled` stays false.
- `Song` <-> `MediaItem` conversion is in `playback/MediaItems.kt`. Media ID = MediaStore audio ID, or `subsonic:<id>` for server songs (URI = authenticated stream URL with the streaming quality settings; artwork = getCoverArt URL). Controllers don't send playback URIs, so the session restores them in `onAddMediaItems` (`withPlaybackUri`). Server songs are scrobbled (now playing on transition, submission when they finish) instead of counted in the local play stats.
- `QueueStore` saves the queue as JSON entries (prefs key `queue`): device songs by ID, server songs with their details (restoring needs no network). Only entries from the current music source restore (`Entry.belongsTo`).
- UI code talks to playback through `PlayerConnection` (Koin single wrapping a `MediaController`). `MainActivity`/`AppWidgetConfigureActivity` call `connect()`/`disconnect()`. Elsewhere use `getPlayer()`/`connectedPlayer()` (null until connected) and the helpers in `extensions/PlaybackExtensions.kt` (`playSong`, `queueSong`, `shuffle`).
- **`MediaController` (so every `PlayerConnection` method) must be called on the main thread**; calling it from a background thread throws "MediaController method is called from a wrong thread". The playback helpers hop to main automatically.
- Change notifications: `playbackEvents()` (a `SharedFlow` of `PlaybackEvents` names: `METADATA_CHANGED`, `PLAYBACK_STATE_CHANGED`, `SERVICE_CONNECTED`). `METADATA_CHANGED` fires often (any timeline/state change), so check whether the song actually changed before doing expensive work. For UI state prefer `PlayerConnection.state` (a `StateFlow<PlayerUiState>`: song, isPlaying, duration, queue, index, repeat, shuffle; composables use `rememberPlayerState()`) and `progress(intervalMs)` for the position.
- Repeat mode is stored in prefs as 1 = one, 2 = all, 3 = none (`RepeatModes` maps to `Player.REPEAT_MODE_*`).

**UI (`ui/`).**
- Jetpack Compose + Material 3 1.5 (Expressive), all under `ui/compose/`. Themes are `MaterialExpressiveTheme` with `MotionScheme.expressive()`. Use the 1.5 APIs: `ListItem(onClick = ..., onLongClick = ...) { headline }` (not `headlineContent` / a clickable modifier), `SegmentedListItem` with `ListItemDefaults.segmentedShapes` for grouped lists, `SortMenu` (a `DropdownMenuPopup` of `DropdownMenuGroup`s with `SelectableDropdownMenuItem`s) for every sort menu, `PageLoadingIndicator` (the expressive `LoadingIndicator`) for loading states, `shapes = ButtonDefaults.shapes()` / `IconButtonDefaults.shapes()` for press morphing, and `SecureTextField` for passwords. `MainActivity` (a `ComponentActivity`) only handles permissions, the player connection, launch intents and delete consent, then calls `setContent { CoffeeApp(...) }`.
- Theming: pages use `SectionTheme` (`theme/SectionTheme.kt`): neutral Coffee surfaces (#181818 / #FAFAFA) with the section's accent as primary, the same colours as the original app and the web player (Home #FF5252, Favorites #FF4081, Library/Search #448AFF, Playlists #FFC400, Settings #FF6E40, Edit #1DE9B6; deeper "ink" shades in light mode). `CoffeeApp` picks the section from the destination (Settings, editor and playlist screens have their own; other detail screens keep the section they were opened from). Top bars show the section name as a `SectionPill` (accent rounded square, uppercase) via `TopLevelScaffold`. Only the mini player and the full player use `CoffeeTheme` (seeded from the current album art via materialkolor, else dynamic colour on 12+). Album and artist pages are fully in their artwork's colours with `ArtworkTint` (`rememberArtworkSeed(model)`; the whole scheme, surfaces included, animating from the section's once the seed loads). Album / artist / playlist cards (`MediaCard`) tint their text area with their artwork's hue (`theme/CardTint.kt`: `rememberCardTint`, a 64px decode, an in-memory LRU by artwork key, and `cardTint` keeping only the hue at a fixed tone with capped chroma, unit tested).
- `CoffeeApp`: a `NavigationSuiteScaffold` (Home, Favorites, Library, Search; bar or rail by window size) around a navigation-compose `NavHost` with type-safe `@Serializable` routes (`navigation/Routes.kt`), the `MiniPlayer`, and the full `PlayerScreen` overlay (queue and lyrics inside; side-by-side when wider than tall).
- Screens: **Home** (`home/`, `HomeViewModel`): album rows for recently added, recently played and most played, plus the user's playlists. On the device these come from MediaStore dates and the app's play stats ("See all" opens the matching smart playlist); on a server, from `getAlbumList2` newest/recent/frequent. **Library** (`library/`): a segmented list of the categories (`LibraryCategory`: Playlists, Albums, Artists, Songs, Genres) above recently played albums (`LibraryOverviewViewModel`). Each category opens its own page (`LibraryCategoryRoute` → `DeviceLibraryCategory` / `ServerLibraryCategory`; Playlists is `playlists/PlaylistsTab`), and only that list loads: server lists start when their page opens (`ServerPager.start`, `ensureArtists`/`ensureGenres`), as each is network calls. **Search** is a top-level tab. **Settings** isn't in the bar: every top-level top app bar ends with `SettingsButton` (`TopLevelScaffold` adds it), which pushes `SettingsRoute`; until a source is set up, `CoffeeApp` opens Settings over Home once.
- Page transitions (`navigation/Transitions.kt`, `PageTransitions` on the `NavHost`) follow Material motion: none between the four top-level destinations (the tapped tab shows at once), shared axis X (30dp slide + cross-fade, reversed on pop and during predictive back) for everything hierarchical (list → detail, detail → detail, Settings). New routes get this automatically; add top-level routes to `topLevelRoutes`. Each tab keeps its own back stack (`navigateTop` in `CoffeeApp`): switching tabs saves the current tab's pages and restores the other tab's (save/restore state), and pressing the active tab again returns to its own page. Tab presses never animate, even when they restore or close a detail page (`PageTransitions.onTabPressed`).
- `AppActions` (provided as `LocalAppActions`) is the shared entry point for playback, navigation, option sheets (`OptionsSheetHost`), dialogs (`AppDialogHost`) and snackbar messages; screens call it rather than wiring those themselves.
- Reusable pieces are in `ui/compose/components/` (song rows, cards, artwork, sort menus backed by `SortSettings`/`SortManager` prefs, dialogs). Reorderable lists use `sh.calvin.reorderable`.
- Settings are a Compose screen over the default `SharedPreferences` (keys in `utils/Config.kt`). Tag writing is in `utils/TagWriter.kt`.
- Images load through Coil 3 (singleton loader configured in `App`). Album art uses the `AlbumArt(albumId, version)` model and `AlbumArtFetcher` (MediaStore `loadThumbnail` on API 29+, where legacy `albumart` URIs don't resolve); server art uses `CoverArt(id, size)`, mapped by `CoverArtMapper` to the signed-in server's URL and cached under a token-free key. Use `song.artworkData()` / `album.artworkData()` to get the right model. Composables use `ui/compose/components/Artwork.kt`; bitmap/artist-image helpers are in `utils/ArtUtils.kt`. The theme seed (Palette) is computed in `ui/compose/theme/Theme.kt`.

**Other.**
- Tag editing uses jaudiotagger 3.0.1 (Maven Central), with `TagOptionSingleton.isAndroid = true` set in `App`. The editor writes only fields that differ from the song as it was when editing started.
- Downloaded artist images are stored in app-private `filesDir/ArtistImages`.
- Home-screen widgets are still RemoteViews in `widget/` (`BaseAppWidget` → `MediumAppWidget`, `BigAppWidget`), with a View-based `AppWidgetConfigureActivity` (the only AppCompat/XML-layout code left).
